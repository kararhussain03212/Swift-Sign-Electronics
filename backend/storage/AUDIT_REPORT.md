## Part 1 — Endpoint audit findings (by cluster)

Four parallel audits covered all 26 controllers / ~90 routes. **13 real bugs found and fixed**, verified live and with `php -l`. Full per-cluster detail in `backend/storage/audit_part1_*.md`.

### 🔴 High severity
| # | Bug | Fix |
|---|---|---|
| 1 | **Order price tampering** — public checkout (`OrderController::publicStore`) trusted client-submitted `item.price` verbatim; "server recompute" just summed attacker-controlled numbers. Verified exploitable: a $190 product could be ordered at $0.01. | Recompute `unit_price = price * (1 - discount/100)` server-side from the DB by `product_id`, ignoring client price entirely. |
| 2 | **Missing permission checks — Hero, Product, Blog create/update.** `HeroController`, `ProductController`, `BlogController` each override the base `store()`/`update()` and dropped the inherited `requirePermission('create_content'/'edit_content')` call. Any authenticated admin — even one without content permissions — could create/edit hero slides, products, or blog posts via direct API calls. | Restored `requirePermission()` in all three controllers. |
| 3 | **User self-privilege-escalation.** An admin/editor holding only `manage_users` could `PUT` their own account's `role` to `admin` and grant themselves full access — only the *protected super admin* account was guarded, not "self" in general. | Blocked self-edits of `role`/`permissions`/`status` in `UserController::update()`; editing one's own name/email/password is unaffected. |

### 🟠 Medium severity
| # | Bug | Fix |
|---|---|---|
| 4 | **Reorder completely broken for Hero and Products.** `BaseModel::reorder()` was hardcoded to write to an `order_position` column, but `hero_slides`/`products`/`categories`/`section_banners` all use `sort_order`. Every call to `PATCH /api/admin/hero/reorder` or `/products/reorder` returned 422 "Failed to reorder items" — the feature never worked. | Added a `sort_order` fallback in `BaseModel::reorder()`. |
| 5 | **Category/Blog-category rename didn't cascade to already-saved content** (same root cause as the products.category bug found before this formal audit) — `blog_posts.category` is also a denormalized name copy. Renaming a blog category orphaned old posts against the stale name. | Added `BlogCategory::renameInPosts()` + a `BlogCategoryController::update()` override, mirroring the products fix. |
| 6 | **Duplicate slug crashes with a raw 500**, leaking the SQL error message to the client. `blog_posts.slug`/`blog_categories.slug` are DB-unique but neither controller pre-checked for collisions before insert, unlike `CategoryController`. | Added `slugExists()` + `uniqueSlug()` disambiguation (`-2`, `-3`, ...) to both `BlogController` and `BlogCategoryController`. |
| 7 | **Nav Link Items / Footer Links: no FK-existence validation.** A bad `nav_link_id`/`group_id` on create threw an uncaught `PDOException` → raw 500 (no global exception handler exists in this app) instead of a clean 422. | Both controllers now verify the parent row exists before insert, returning 422 on a bad reference. |
| 8 | **Orphaned upload files — Section Banner background image, and all 5 About-page image fields** (team member photo, testimonial avatar, value-card image, hero image, CEO photo). Forms called the uploader without the `oldPath` argument, so every image replace left the previous file behind in `backend/uploads/` forever. | Threaded the current field value through as `oldPath` in `SectionBannerForm.jsx` and all 4 About admin forms. |

### 🟡 Low severity
| # | Bug | Fix |
|---|---|---|
| 9 | `"about"` missing from `FileUpload::ALLOWED_FOLDERS` — About-page uploads silently fell into `misc/` instead of their own folder (files still worked, just disorganized). | Added `'about'` to the allow-list. |

### Ruled out / flagged as architecture-level (not fixed, per scope)
- Nav Link Items / Footer Links orphan-on-parent-delete — DB already has `ON DELETE CASCADE`, confirmed via `SHOW CREATE TABLE`. Not a bug.
- No rate limiting beyond `/login` (contact form, `changePassword`, public orders unthrottled) — flagged, not built, per audit-agent instructions to avoid new infrastructure.
- `CustomerAddressController` uses raw parameterized SQL instead of the model layer — inconsistent style, not a security/correctness bug.
- Product gallery images (multi-image, not 1:1 replace) don't clean up removed images the same way single-image fields do — flagged as a possible future enhancement, not a bug (no well-defined "old" slot to clean).

All fixes verified with `php -l` (zero syntax errors across the entire `backend/` tree) and live smoke tests against the local API/DB; all test data created during verification was deleted afterward.

### 🟠 Bug found and fixed: Admin "Contact Messages" page always showed empty
`ContactController::index()` (`backend/controllers/ContactController.php:263-271`) returns a **paginated** response shape — `{ success, data: { data: [...], meta: {...} }, message }` — but `admin/src/pages/contact/ContactMessages.jsx:36-38` only unwrapped one level (`res.data.data`, expecting it to already be the array), so `Array.isArray()` failed and the page always rendered "no messages," regardless of how many real submissions existed in the database. The dashboard's separate "Unread Msgs" counter (different endpoint) worked fine, which is why this wasn't obvious at a glance — only the dedicated Contact Messages list page was broken.

**Found via**: submitting a real contact form message through the public API, confirming it landed correctly in the `contact_messages` table, then discovering the admin list endpoint's raw JSON *did* contain it — but the rendered admin page showed nothing.

**Fix**: `ContactMessages.jsx` now unwraps `res.data.data.data` (matching the same nested-pagination pattern already handled correctly by `UserManagement.jsx` for the Users list, which uses an identical `{data:{data,pagination}}` shape).

**Verified live**: submitted a real message via the public contact form, confirmed it was invisible on the admin page before the fix and visible after, via a real browser screenshot. Test message deleted afterward.

**Also checked for the same bug pattern** in Users (`UserManagement.jsx` — correct, already unwraps `response.data?.data?.data`), Orders and Customer Addresses (`OrderController`/`CustomerAddressController` both return flat, non-paginated `data` arrays — no mismatch possible). Confirmed isolated to this one page.

### 🔴 Critical bug found via E2E testing and fixed: every direct link to a product page redirected to the homepage
`src/pages/ProductDetails.jsx` read from `ShopContext`'s `products` array, which starts empty and populates asynchronously. The "product not found → redirect home" effect fired on first render, before the async fetch resolved, so it always redirected — meaning **any deep link, shared link, bookmark, or plain page refresh of a product page silently bounced the visitor to the homepage**, site-wide, for every single product. Client-side navigation (clicking a product card) masked this because `products` was already loaded by then.

**Fix**: added a `productsLoaded` flag to `ShopContext` (`src/context/ShopContext.jsx`), set once the initial fetch settles; `ProductDetails.jsx` now only redirects when `productsLoaded && !product`. Re-verified: full E2E scenario re-run green, including three separate direct-URL loads.

### 🟡 Minor bug found via E2E testing and fixed: deleting a product left its image file(s) orphaned on disk
Confirmed by observing orphaned `img_*.webp` files accumulate in `backend/uploads/` after every product delete, even though the DB row was correctly removed. Fixed in `ProductController::destroy()` (new override, `backend/controllers/ProductController.php`) — now deletes the thumbnail and every gallery image via `FileUpload::deleteExistingUpload()` (made public for reuse) before removing the row. Verified live: created a product with an uploaded image, deleted it, confirmed the file was gone from `backend/uploads/`.

## Follow-up — architecture-level items closed out

The four hardening gaps flagged earlier in this report (originally left open as "not quick patches") were subsequently fixed and verified:

1. **Rate limiting added** to `/api/public/contact` (5/5min per IP), `/api/public/orders` (10/5min), and `/api/auth/password` (5/5min), via a new shared `backend/utils/RateLimiter.php` (mirrors the file-backed sliding-window approach `AuthController::ensureRateLimit()` already used for login, generalized into a reusable utility). Verified live: 6 rapid contact-form submissions → 6th returns `429`.
2. **`CustomerAddressController` refactored** off raw inline SQL onto a new `backend/models/Customer.php` model (`allWithAddresses()` for the admin list view, `find()` for single-customer lookup via the inherited `BaseModel`), matching the rest of the codebase's controller→model separation. Verified live: `/api/admin/customers` still returns correctly after the refactor.
3. **Gallery image cleanup on partial removal** — `ProductController::update()` now diffs the old vs. new `thumbnail`/`images` set on every save and deletes whatever's no longer referenced (not just on full product delete). Verified live: uploaded 2 gallery images, removed 1 via update, confirmed only the removed one was deleted from `backend/uploads/` while the kept one and the still-live product were untouched.
4. **Global exception handler hardened** (`backend/index.php`) — the top-level `catch (Throwable)` now logs the real exception via `error_log()` and returns a generic "Server error. Please try again later." message when `APP_ENV=production`, instead of echoing `$e->getMessage()` (which could contain SQL text, file paths, or stack trace fragments) straight to the client. Local/dev (`APP_ENV=local`) is unchanged — still shows the real message for debugging.

Full PHPUnit suite (14/14) re-run and confirmed green after all four fixes; both frontend apps rebuild clean; full backend `php -l` sweep clean.
